# Simplify

协议版本：`0.3.0`。适用性与模式由 [using-simplify](../using-simplify/SKILL.md) 唯一维护。缺少模式时自行读取并补全，不向用户索取内部流程参数。

## 审查范围与深度

检查本任务实际 diff 和直接受影响路径，保留其他人的修改。已提交改动使用任务起点或保存的 diff；没有 Git 时使用修改前后文件对照。

- Lite：主 Agent 做一次简短自审，不默认分派 reviewer 或输出结构化报告。
- Standard：按相关轨道完成审查；独立子任务能增加可信度时可以委派，不要求每轨一个 Agent。
- Strict：对关键行为与失败路径取得更强证据，适用时进行独立只读审查；不因模式名称自动跑全量测试。独立审查不可用时说明限制，不能声称已经完成独立检查。

轨道作为审查视角，可在一次检查中完成：

- `feature`：`repo_fit`、`quality`、`reuse`。
- `refactor`：`quality`、`repo_fit`、`reuse`。
- `bugfix`：`blast_radius`、`repo_fit`、`quality`。
- 只有热路径、循环调用、新增 I/O 或重复转换等实际变化时加入 `efficiency`。

检查仓库模式、行为影响、冗余状态、重复实现和不必要抽象。复用建议必须比当前实现更简单且不扩范围，不为消除几行重复创建通用框架。

## Findings 与取舍

只上报有具体位置、问题、影响和证据的发现。没有问题可返回 `no_issues`；存在发现用 `ok`；无法完成检查用 `blocked` 并说明原因。无需为凑数量创造问题。

- P0：严重且紧急的安全、数据损失或广泛不可用风险。
- P1：显著错误行为、关键回归或重要约束违反。
- P2：影响有限但有实际收益的正确性或维护问题。
- P3：可选建议。

主 Agent 核验并归类：`must_fix` 为妨碍目标、正确性或重要约束的问题；`fix_if_cheap` 为低成本、不扩范围且收益明确的改善；`note_only` 为非阻塞建议。维护偏好不自动成为 must_fix。

报告保持精简，但不能用数量上限或 Lite 模式隐藏已知正确性、安全问题。多条重复发现合并，非关键细节可以留在工作记录。

## 修正、验证与结束

修复确认的 must_fix，选择性处理 fix_if_cheap。发现超出授权的必要修复时准备具体方案并说明阻塞，不擅自扩权。reviewer 仅审查，不负责实现或再触发 simplify。

修正后先验证受影响路径，再运行适用的任务验证；仅当风险扩大或存在新证据时扩展范围。已有检查覆盖当前最终内容且未修改时复用结果，不为收尾仪式重新运行。

一次审查加受影响修正复查通常足够；仍有具体严重问题则继续处理。不得无限追逐美化或重新分类。

无值得处理的问题时输出 `no cleanup needed`，依据应来自实际 diff 与验证，可以是影响清晰、沿用既有模式、无冗余抽象或重复状态。较大改动也允许该结论。

收尾简述模式、类型、实际轨道、已修问题或无需清理的证据，以及验证和真实限制。不要为每个空字段生成一段报告。
