# Luna 编排

本 Skill 只在用户显式调用 `$luna-orchestrator` 后生效。它覆盖当前任务及同一任务的后续跟进，任务完成后结束，不自动影响新任务；用户也可以提前明确停用。停用后恢复宿主原有工作方式，不修改全局指令、Agent 配置或模型默认值。

## 角色边界

- 主 Agent 持有目标和范围，读取现状，拆解任务，定义接口与依赖，安排调度，并做只读核验和最终验收。
- Luna worker 承担所有实施：写文件、运行测试或验证器、诊断和修复失败、集成改动、提交以及发布。主 Agent 不直接接管这些动作。
- 委派提交或发布不等于获得远程授权。每次远程操作仍须符合用户已经给出的授权范围；没有授权就完成准备和核验，在对应边界暂停。
- worker 只执行收到的任务，不递归扩员、不自行扩大范围、不把未验证的判断当作验收。需要新增任务时回报主 Agent，由主 Agent 重新拆解和调度。

## 确认可用的 Luna

调度前先确认宿主实际支持的代理工具和模型：

1. 优先使用宿主注册的具名 `luna_worker`，但先依据当前工具元数据或角色配置确认其实际模型为 `gpt-5.6-luna`；无法确认时不能把它当作已确认的 Luna，转到下一条显式模型路径。
2. 具名角色不可用或无法确认其模型时，只有在实际调度工具明确支持 `gpt-5.6-luna` 时，才可显式指定该模型作为替代，并在任务记录和回报中如实说明替代关系。
3. 两者都不可用时，只能完成只读调查、拆解和阻塞报告；不能用其他模型冒充 Luna，也不能让主 Agent 默默接管实施。只有用户明确允许主 Agent 接管后，才可离开本委派边界继续实施。

## 拆解与调度

先做只读检查，确认目标、现有改动、仓库边界、运行入口和依赖。然后按真实文件所有权和依赖关系拆分；任务总数不设固定上限，持续寻找有清晰边界的独立工作，直到没有有价值的独立任务或宿主实时容量已满。

每个委派包都写清以下内容：

```text
目标：本任务要产生的可观察结果
范围：允许处理的路径、接口和行为；明确不包含的范围
文件所有权：本 worker 可写的文件，逐文件唯一归属
前置依赖：必须先完成的任务、输入或接口
验收：要运行的命令、要检查的行为和通过条件
证据：需要回报的 diff、日志、产物、哈希或链接
并发保护：与哪些任务互斥、何时交给集成 worker
```

独立文件或互不重叠的接口可以并行派发；同一文件始终只有一个写者，后续修改排队串行。依赖完成后再派发集成任务，并指定唯一的集成 worker。派发集成或修复 worker 前，主 Agent 先确认原 worker 已结束或停止写入，明确收回并重新分配文件所有权；原 worker 不得继续写入。所有并行调度都服从宿主工具前提、工具允许的并行度和实时容量；容量变化时动态补充队列、复用已完成的 worker。不假定固定并发数，不以“多派了几个”代替独立性判断。

主 Agent 可以继续做只读定位、读取 worker 输出、比较实际 diff、检查状态和核对目标路径，但测试、验证器和会改变工作区或外部状态的命令都交给 Luna worker 执行。后续测试或修复任务是原任务的执行分支，不再次套用本 Skill 递归调度。

## 失败、修复与审阅

测试或验收失败时保留失败命令和原始证据，立即把诊断、修复及重跑委派给合适的 Luna worker；不降低断言、不删检查、不把失败改写成通过。修复仍遵守逐文件写者和依赖顺序。

实施和审阅分开：风险足够高时，实施完成后安排另一名可用 Luna worker 做独立审阅，审阅目标、输入和验收标准单独写明。主 Agent 汇总实施与审阅证据，核对实际 diff 和用户目标；worker 的“完成”回报本身不构成验收。

## 完成条件

主 Agent 只有在以下证据齐全后才报告完成：目标范围内的实际 diff 与工作区状态已只读核对；每个任务的依赖、文件所有权和验收结果可追溯；所有必要任务和验证均已满足；测试和验证输出来自实际 Luna worker；必要的集成、提交或发布在用户授权范围内完成。若必要任务或验证仍阻塞，只能报告部分完成并说明阻塞，不能把阻塞报告为完成。最终回报注明实际使用的 Luna 入口、关键证据、未完成项和仍需用户决定的权限边界。
