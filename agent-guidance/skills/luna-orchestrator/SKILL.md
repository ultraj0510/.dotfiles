# Luna 编排

本 Skill 只在用户显式调用 `$luna-orchestrator` 后生效。它覆盖当前任务及同一任务的后续跟进，任务完成后结束，不自动影响新任务；用户也可以提前明确停用。停用后恢复宿主原有工作方式，不修改全局指令、Agent 配置或模型默认值。

## 角色边界

- 主 Agent 持有目标和范围，读取现状，拆解任务，定义接口与依赖，安排调度，并做只读核验和最终验收。
- Luna worker 承担所有实施：写文件、运行测试或验证器、诊断和修复失败、集成改动、提交以及发布。主 Agent 不直接接管这些动作。
- 委派提交或发布不等于获得远程授权。每次远程操作仍须符合用户已经给出的授权范围；没有授权就完成准备和核验，在对应边界暂停。
- worker 只执行收到的任务，不递归扩员、不自行扩大范围、不把未验证的判断当作验收。需要新增任务时回报主 Agent，由主 Agent 重新拆解和调度。

## 确认可用的 Luna

调度前先确认宿主实际支持的代理工具和模型：

1. 优先使用宿主注册的具名 `luna_worker`，但先依据当前工具元数据或角色配置确认其实际模型为 `gpt-6-luna`；无法确认时不能把它当作已确认的 Luna，转到下一条显式模型路径。
2. 具名角色不可用或无法确认其模型时，只有在实际调度工具明确支持 `gpt-6-luna` 时，才可显式指定该模型作为替代，并在任务记录和回报中如实说明替代关系。
3. 两者都不可用时，只能完成只读调查、拆解和阻塞报告；不能用其他模型冒充 Luna，也不能让主 Agent 默默接管实施。只有用户明确允许主 Agent 接管后，才可离开本委派边界继续实施。

## 拆解与调度

先做只读检查，确认目标、现有改动、仓库边界、运行入口和依赖。主 Agent 亲自建立轻量任务树并统一派发叶子节点；worker 不递归拆解、不扩员。树表示父节点对目标的包含关系：每个父节点写清子目标、范围和父级验收；每个叶子写清输入、唯一文件归属、依赖和叶级验收，并为跨分支依赖另行记录。拆解深度随任务而定：简单任务可以只有一层；继续拆解的终点是得到可执行的叶子，不以并发容量决定。容量只约束当前派发数量和调度顺序。

树和节点记录默认保留在当前会话内；已有项目任务记录或用户要求持久化时沿用既有位置和格式，不为任务树额外搭建框架。节点可使用轻量标识（例如 `P1`、`L1`）；父节点和叶子至少包含以下字段：

```text
父节点 Pn
子目标：本节点包含的结果
范围：允许处理的路径、接口和行为；明确不包含的范围
子节点：直接包含的节点标识
父级验收：目标、范围、子节点结果和集成证据均满足的检查

叶子 Ln
输入：已确认的文件、接口、日志或上游产物
目标/范围：本叶子要产生的可观察结果及边界
文件所有权：本 worker 可写的文件，逐文件唯一归属
前置依赖：必须先完成的节点、输入或接口
叶级验收：要运行的命令、要检查的行为和通过条件
证据：需要回报的 diff、日志、产物、哈希或链接
并发保护：与哪些任务互斥、何时交给集成或修复 worker

跨分支依赖：Ln <- Lm（依赖内容、满足条件和派发顺序）
```

独立文件或互不重叠的接口可以并行派发；同一文件始终只有一个写者，后续修改排队串行。所有实施、测试、验证器和集成改动都由 Luna worker 执行，主 Agent 保持只读。需要集成时，依赖完成后把集成验证写成显式叶子（包含其输入、唯一文件归属、依赖和验收）；简单任务的验证可以留在原叶子内，不要把父节点的验收描述替代必要的集成叶子。

worker 发现新问题、缺少输入或需要扩大范围时，只回报主 Agent；主 Agent 动态调整任务树、依赖和派发，不允许 worker 自行扩展。重新拆分正在执行的叶子，或任何集成或修复 worker 接手前，主 Agent 先确认原 worker 已结束或停止写入，明确收回并重新分配文件所有权；原 worker 在收回后不得继续写入。所有并行调度都服从宿主工具前提、工具允许的并行度和实时容量；容量变化时动态补充队列、复用已完成的 worker。不假定固定并发数，不以“多派了几个”代替独立性判断。

主 Agent 可以继续做只读定位、读取 worker 输出、比较实际 diff、检查状态和核对目标路径，但测试、验证器和会改变工作区或外部状态的命令都交给 Luna worker 执行。后续测试或修复任务是原任务的执行分支，不再次套用本 Skill 递归调度。

## 主动监督与停滞恢复

主 Agent 派发每个叶子时，同时记录该叶子的预期阶段、下一项可观察进度证据、检查方式和按任务复杂度设定的最长无状态窗口。窗口是该叶子的任务阈值，不设所有任务通用的固定时长；任务记录要能说明 worker 当前处于什么阶段、下一里程碑是什么以及超时后如何处理。

长任务必须按可观察里程碑报告进度，不能只等待 worker 的最终回报。里程碑可以是已修改文件或 diff、测试或验证器的开始与结束、提交哈希、部署或发布标识、外部状态变化或原始错误日志；没有这些证据时只能记为未确认进度。

到达该叶子设定的无状态窗口而没有约定的进度证据时，主 Agent 先做只读状态检查，至少查看 agent 的运行或退出状态、目标文件和工作区 diff、worker 已产生的日志或测试输出、提交状态以及已有外部操作的状态。主 Agent 记录检查时间、实际结果和原始错误，再决定继续等待或启动恢复；不能把没有新消息当作完成。

检查表明无进度或无响应时，主 Agent 先要求当前 worker 立即报告当前阶段、已完成产物、错误和下一步；只有该请求仍无响应或没有新增进展时，才中断 worker。中断前后保存已完成产物、diff、日志、提交信息和错误证据，确认 worker 已结束或停止写入后收回文件所有权，再改派诊断、修复或集成任务；原 worker 收回后不得继续写入。临时 worktree 可以帮助恢复，不能作为唯一完成证据。

遇到网络、凭据或沙箱边界时，先用最小探测区分 DNS 或连通性、认证、权限和执行环境限制，并保留原始错误；在已有授权范围内确有必要时，改用受授权的主机网络或执行环境继续验证，不能反复等待来替代诊断，也不能借此扩大远程操作授权。

## 失败、修复与审阅

测试或验收失败时保留失败命令和原始证据，立即由主 Agent 在任务树中增加或改派诊断、修复及重跑叶子，再委派给合适的 Luna worker；不降低断言、不删检查、不把失败改写成通过。修复仍遵守逐文件写者和依赖顺序。

实施和审阅分开：风险足够高时，实施完成后安排另一名可用 Luna worker 做独立审阅，审阅目标、输入和验收标准单独写明。主 Agent 汇总实施与审阅证据，核对实际 diff 和用户目标；worker 的“完成”回报本身不构成验收。

## 完成条件

主 Agent 只有在以下证据齐全后才报告完成：目标范围内的实际 diff 与工作区状态已只读核对；每个叶子的依赖、文件所有权和叶级验收结果可追溯；必要的集成验证叶子已完成；每个父节点的目标、范围和父级验收均由主 Agent 根据实际 diff 与必要的集成证据核对，而非依据子节点“完成”回报推定；所有必要任务和验证均已满足；测试和验证输出来自实际 Luna worker；必要的集成、提交或发布在用户授权范围内完成。若必要任务或验证仍阻塞，只能报告部分完成并说明阻塞，不能把阻塞报告为完成。最终回报注明实际使用的 Luna 入口、关键证据、未完成项和仍需用户决定的权限边界。

最终报告必须明确区分三类结论：worker 的实施完成回报、主 Agent 对实际 diff 和验证证据的只读验收、以及外部提交或发布后的独立状态核验。缺少其中所需的一类时，只能报告相应阶段已完成，不能把 worker 的完成回报写成整体完成或把本地验收写成外部发布已核验。
